# Accounts Payable Control System
## Backend Schema & Production-Oriented Architecture

**Document:** Backend Schema & Architecture Specification  
**Version:** 1.0  
**Status:** Hackathon-ready / Production-oriented foundation

---

## 1. Backend Objective

The backend is the authoritative control layer between invoice intake and creation of a payable obligation.

The backend must guarantee that:

1. Every invoice belongs to a tenant/company.
2. Every invoice is processed idempotently.
3. Financial validation is deterministic and reproducible.
4. Purchase Order (PO), Goods Receipt (GR), Vendor, and Invoice relationships are explicit.
5. Approval and state transitions are server-authorized.
6. AI results are treated as signals/evidence, not final payment authorization.
7. Payable creation happens only through a successful controlled transition.
8. Audit records are append-only and immutable from the application layer.
9. Sensitive vendor/payment information is access-controlled and encrypted where appropriate.
10. Background work is durable, retryable, observable, and safe to execute more than once.

# 2. Recommended Backend Stack

| Layer | Technology | Reason |
|---|---|---|
| API | FastAPI + Python 3.12+ | Typed, fast, ideal for document/AI workloads |
| ORM | SQLAlchemy 2.x | Mature PostgreSQL integration |
| Migrations | Alembic | Versioned schema migrations |
| Validation | Pydantic v2 | Strong request/domain validation |
| Database | PostgreSQL 16+ | Transactions, constraints, JSONB, mature relational model |
| Vector Search | pgvector | Semantic invoice similarity without another database |
| Queue | Redis + Celery | Durable asynchronous processing and retries |
| Object Storage | S3-compatible / Supabase Storage | Invoice source documents and artifacts |
| Auth | Supabase Auth or external IdP + JWT | Authentication |
| Authorization | Application RBAC + PostgreSQL RLS where applicable | Tenant/role isolation |
| Observability | OpenTelemetry + structured logging | Traceability |
| Testing | Pytest | Backend/unit/integration tests |
| API docs | OpenAPI generated by FastAPI | Contract visibility |

### Architecture principle

Prefer a **modular monolith** for the hackathon instead of microservices. Keep domain boundaries explicit so individual modules can later be extracted into services.

Every business record must be scoped to a `tenant_id`.

```text
  +-- Goods Receipts
```

# 6. PostgreSQL Schema

## 6.1 tenants

Stores organization/company boundaries.

```sql
CREATE TABLE tenants (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    name VARCHAR(200) NOT NULL,
    code VARCHAR(50) NOT NULL UNIQUE,
    base_currency CHAR(3) NOT NULL DEFAULT 'INR',
    timezone VARCHAR(64) NOT NULL DEFAULT 'Asia/Kolkata',

    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
```

# 14. Duplicate Detection Schema

## 14.1 invoice_fingerprints

```sql
CREATE TABLE invoice_fingerprints (
    invoice_id UUID PRIMARY KEY REFERENCES invoices(id) ON DELETE CASCADE,
    exact_fingerprint CHAR(64) NOT NULL,
    normalized_fingerprint CHAR(64) NOT NULL,
    embedding VECTOR(384),
    generated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

Create indexes appropriate to your pgvector version for nearest-neighbor searches.

### Detection levels

```text
Level 1 -> File SHA-256
Level 2 -> Exact vendor + invoice number
Level 3 -> Normalized invoice fingerprint
Level 4 -> Vendor + amount + PO + date similarity
Level 5 -> Semantic line-item/document similarity
```

The first four levels can run quickly before invoking embeddings.

# 17. Payable Ledger

The payable ledger is a **derived financial obligation record**, created only after the invoice passes required controls and approvals.

```sql
CREATE TABLE payable_ledger (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id UUID NOT NULL REFERENCES tenants(id),
    invoice_id UUID NOT NULL UNIQUE REFERENCES invoices(id),
    vendor_id UUID NOT NULL REFERENCES vendors(id),
    approved_amount NUMERIC(18,2) NOT NULL,
    currency CHAR(3) NOT NULL,
    due_date DATE,
    payable_status VARCHAR(30) NOT NULL DEFAULT 'OPEN'
        CHECK (payable_status IN ('OPEN', 'SCHEDULED', 'PAID', 'ON_HOLD', 'CANCELLED')),
    approved_at TIMESTAMPTZ NOT NULL,
    scheduled_payment_at TIMESTAMPTZ,
    paid_at TIMESTAMPTZ,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

### Critical invariant

```text
One invoice -> zero or one payable record.
```

Use a unique constraint on `invoice_id` to prevent double creation.

# 19. Idempotency

This is essential for invoice systems.

A vendor may retry an upload because of a network failure.

The same API request must not create two invoices.

## idempotency_keys

```sql
CREATE TABLE idempotency_keys (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id UUID NOT NULL REFERENCES tenants(id),
    idempotency_key VARCHAR(150) NOT NULL,
    request_hash CHAR(64) NOT NULL,
    response_status INTEGER,
    response_body JSONB,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (tenant_id, idempotency_key)
);
```

Recommended for:

```text
POST /invoices
POST /invoices/{id}/process
POST /invoices/{id}/approve
POST /invoices/{id}/reject
POST /invoices/{id}/payable
```

# 20. Invoice Processing Pipeline

```text
1. Upload document
2. Validate MIME type / size
3. Store document
4. Create invoice shell
5. Enqueue processing job
6. OCR
7. Extract structured fields
8. Normalize vendor/date/amount/tax fields
9. Resolve vendor
10. Resolve PO
11. Resolve receipt coverage
12. Generate invoice fingerprint
13. Run exact duplicate checks
14. Run semantic similarity checks
15. Run financial controls
16. Generate control_results
17. Generate risk_signals
18. Create exceptions if needed
19. Resolve approval policy
20. Transition invoice state
21. Emit audit events
22. Notify relevant role
```

# 21. Background Job Design

Use Celery + Redis.

```text
invoice.uploaded
        |
        v
process_invoice
        |
        +--> ocr_invoice
        |
        +--> extract_invoice
        |
        +--> normalize_invoice
        |
        +--> compute_fingerprint
        |
        +--> find_duplicates
        |
        +--> run_controls
        |
        +--> create_exceptions
        |
        +--> route_approval
```

### Jobs must be idempotent

A worker retry must never:

- create a second payable
- duplicate an approval request
- create duplicate audit records where uniqueness can be enforced
- overwrite a newer invoice version

Use unique job keys/business constraints where needed.

# 22. Control Engine Design

Do not hard-code every control inside one enormous function.

Use a registry:

```python
CONTROL_REGISTRY = {
    "PO_EXISTS": PoExistsControl(),
    "PO_VENDOR_MATCH": PoVendorMatchControl(),
    "QUANTITY_MATCH": QuantityMatchControl(),
    "RECEIPT_COVERAGE": ReceiptCoverageControl(),
    "PRICE_MATCH": PriceMatchControl(),
    "TAX_MATCH": TaxMatchControl(),
    "TOTAL_MATCH": TotalMatchControl(),
    "EXACT_DUPLICATE": ExactDuplicateControl(),
    "SEMANTIC_DUPLICATE": SemanticDuplicateControl(),
    "VENDOR_BANK_MATCH": VendorBankMatchControl(),
}
```

Each control returns a standard result:

```python
ControlResult(
    code="PRICE_MATCH",
    status="FAIL",
    severity="HIGH",
    actual_value={"invoice_price": 52000},
    expected_value={"po_price": 50000},
    variance_value=2000,
    variance_percent=4.0,
    explanation="Invoice unit price is 4% above the approved PO price.",
)
```

This gives you:

- independent unit testing
- reusable controls
- versioning
- transparent explanations
- configurable policies later

# 23. Three-Way Match Algorithm

For each invoice line, resolve a corresponding PO line and accepted receipt quantity.

### Step 1: PO resolution

```text
invoice.po_number -> purchase_orders
```

If no PO:

```text
PO_EXISTS = FAIL
```

### Step 2: Line mapping

Prefer:

```text
product_code
```

then normalized description similarity where product code is unavailable.

### Step 3: Quantity control

```text
invoice_qty <= accepted_receipt_qty + allowed_tolerance
```

### Step 4: Price control

```text
abs(invoice_unit_price - po_unit_price) <= price_tolerance
```

### Step 5: Total control

Recalculate from line items rather than trusting the invoice total.

### Step 6: Tax control

```text
expected_tax = taxable_base * tax_rate
```

### Step 7: Final match status

```text
PASS
WARN
FAIL
```

Never collapse warnings and failures into one generic result.

# 28. Concurrency and Transaction Strategy

Approval and payable creation are race-condition hotspots.

### Example

Two finance users click Approve simultaneously.

Backend should:

```text
BEGIN TRANSACTION
   SELECT invoice FOR UPDATE
   verify state
   verify user permission
   verify approval requirements
   create/update approval
   if all approvals complete:
       create payable if absent
       transition invoice
   write audit event
COMMIT
```

The database unique constraint on `payable_ledger.invoice_id` acts as a second line of defense.

# 31. Data Integrity Rules

These are non-negotiable backend invariants.

### Invoice

```text
Invoice cannot be APPROVED when:
- mandatory control is FAIL
- blocking exception is OPEN
- required approval is incomplete
```

### Payable

```text
Payable cannot be created when:
- invoice is not APPROVED
- invoice already has payable
- vendor is BLOCKED
```

### Payment

```text
Paid cannot be set when:
- payable is CANCELLED
- payable is ON_HOLD
```

### Editing

```text
Approved invoices are immutable for financial fields.
Any correction creates a new revision/version and a new control run.
```

# 32. Invoice Versioning

Do not simply overwrite approved invoice data.

Recommended structure:

```text

  |
  +-- revision 1
  +-- revision 2
  +-- revision 3
```

Schema:

```sql
CREATE TABLE invoice_revisions (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    invoice_id UUID NOT NULL REFERENCES invoices(id) ON DELETE CASCADE,
    revision_number INTEGER NOT NULL,
    extracted_data JSONB NOT NULL,
    normalized_data JSONB NOT NULL,
    document_id UUID REFERENCES documents(id),
    created_by UUID REFERENCES users(id),
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE(invoice_id, revision_number)
);
```

Every revised invoice gets a fresh control run.

# 40. Recommended Repository Pattern

Example service:

```python
class InvoiceApprovalService:
    def approve(self, invoice_id: UUID, actor: User):
        invoice = self.invoice_repo.get_for_update(invoice_id)

        self.permission_service.require(actor, "invoice.approve")
        self.state_machine.require_transition(invoice, "APPROVED")
        self.control_service.require_no_blocking_failures(invoice)
        self.approval_service.require_current_approval(actor, invoice)

        invoice.status = InvoiceStatus.APPROVED
        self.payable_service.create_if_absent(invoice, actor)
        self.audit_service.record(...)

        self.db.commit()
```

The important point is that the controller only orchestrates; it should not contain financial business logic.

# 47. Golden Rules for the Implementation

1. **Database is authoritative** for financial state.
2. **Backend enforces authorization**; never trust client roles/status.
3. **Every financial decision has evidence.**
4. **Every state transition is validated server-side.**
5. **Every important mutation creates an audit event.**
6. **Every invoice processing job is idempotent.**
7. **Approved invoices are immutable; corrections become revisions.**
8. **AI produces assistance/signals; deterministic controls decide financial validity.**
9. **Payable creation is transactional and unique per invoice.**
10. **Use a modular monolith now; keep domain boundaries clean for future scaling.**
